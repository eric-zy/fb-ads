# 风控中心完善任务计划

> 目标：在现有 Meta 广告投放系统基础上，把“账户风险概览”完善为可配置、可审计、可回滚核查的风控与自动止损闭环。
>
> 本计划只作为当前代码库的实施基线，不引入第二套数据库实体或新的 Meta SDK 调用链。所有长耗时检查和止损动作继续通过 Celery/现有 `services/meta/` 执行。

## 一、现状结论

### 已有能力

- 已有 `RiskEvent`、`RiskRule`、账户 `risk_score` 和 `last_risk_check` 字段。
- 已有账户健康检查、欺诈评分、风险事件、发布频次、API 限流估算等接口。
- 已有 `RiskDetector`、账户冻结、异常花费检测、基础自动暂停和每小时 Celery 风险检查。
- 已有租户过滤、账户访问范围校验和基础风险回归测试。
- 现有风险页面已经具备截图中的三段式结构：状态卡片、风险事件、系统建议。

### 主要缺口

1. **页面范围不清晰**：当前页面依赖一个选中的广告账户；截图表现为风控中心总览，但没有“全部账户/单账户”的明确切换和汇总指标。
2. **路由存在两套口径**：实际页面使用 `/dashboard/risk-control`，导航常量还保留未接通的 `/app/risk/accounts`、`/app/risk/stops`、`/app/risk/rules`。
3. **规则不可配置**：`RiskRule` 目前只有固定阈值、动作和通知字段，未支持 `scope`、`conditions[]`、`logic`、最小数据量、冷却时间、每轮动作上限、dry-run、白名单等。
4. **检测与止损未形成独立执行记录**：风险事件记录了结果，但没有保存规则版本、命中条件、指标快照、目标对象、幂等键、Meta 返回结果和每次执行状态。
5. **重复执行风险**：当前检测每小时运行，异常事件和暂停动作缺少统一的 cooldown、幂等和最大动作数保护。
6. **人工处理闭环不足**：事件列表没有分页、筛选、详情、确认/解决和处理记录；系统建议没有关联到可执行动作。
7. **前端存在数据展示问题**：发布频次时间窗口和默认值硬编码；页面轮询清理方式不正确，组件反复进入时可能累积定时器。
8. **数据一致性和安全边界需要补强**：风险相关查询需统一租户和账户范围过滤；自动动作必须使用现有投放动作记录和审计日志，不能只改本地状态。

## 二、目标范围与明确不做项

### V1 必须完成

- 风控总览：全部可见账户汇总 + 单账户详情。
- 风险事件查询、筛选、详情、人工解决和审计。
- 风控规则 CRUD、启停、优先级、规则预览和 dry-run。
- Spend 无转化、ROI、CPA 三类规则的条件模型。
- minimum spend、minimum runtime、cooldown、max actions per run、人工白名单、全局 kill switch。
- 自动动作只支持暂停，不做默认自动恢复。
- 止损执行记录与风险事件分开展示。
- Celery 异步执行、幂等、二次校验、失败重试和告警通知。
- 租户隔离、RBAC、审计和关键流程自动化测试。

### V1 不纳入

- 自动恢复、自动扩量、智能预算。
- TikTok/Google Ads 等新平台。
- 重写现有账户、Insights、Job Center 模型。
- 用前端隐藏替代服务端权限控制。
- 直接从 Controller 调用 Meta SDK。

- [ ] 如需拆分大批次，增加动作明细模型，记录每个 campaign/adset/ad 的 before/after 状态、幂等键、任务 ID、Meta 结果和重试次数。

### RC-02 风控 API 与权限（P0）

**任务**

- [ ] 增加风控总览接口：返回账户状态分布、风险等级分布、未解决事件数、今日暂停数、规则命中数、最近检查时间和数据新鲜度。
- [ ] 增加风险账户列表接口：支持账户、BM、风险等级、状态、事件状态、时间范围、分页和排序。
- [ ] 改造风险事件接口：支持分页、等级/类型/解决状态筛选、事件详情和关联对象。
- [ ] 增加事件“标记处理中/解决”接口，要求记录处理人、处理时间、处理说明，并写入审计日志。
- [ ] 增加规则列表、新建、编辑、启停、复制、预览和 dry-run 接口。
- [ ] 增加止损执行记录列表和详情接口，与风险事件接口分离。
- [ ] 增加手动触发检查和全局 kill switch 接口；长耗时操作只返回任务 ID。
- [ ] 统一所有风控查询的租户过滤、账户访问范围和 RBAC：规则管理至少需要 `admin/manager`，查看/处理权限按产品权限点定义。

**建议涉及文件**：新增 `api/risk_control.py`，在 `main.py` 注册；复用 `core/tenant.py`、`core/auth.py`、`core/audit.py`。

**验收**：跨租户、越权账户、平台内置规则修改、无权限执行动作均有自动化测试覆盖。

### RC-03 规则评估与安全护栏（P0）

**目标**：把当前固定阈值检测收敛为可解释、可控制的规则引擎。

**任务**

- [x] 定义条件 DSL：指标、运算符、阈值、窗口、最小数据要求和单位；先支持 spend、conversions、ROI、CPA、CTR、CPC。
- [x] 实现 `AND/OR` 条件组合和规则命中解释结果。
- [x] 实现 minimum spend、minimum runtime、cooldown；每轮最大动作数留到 RC-04 执行器实施。
- [x] 实现账户/系列/广告组/广告的 scope 与白名单跳过逻辑。
- [x] 实现 dry-run：读取本地 Insights 生成命中结果和预期动作，不调用 Meta 写接口。
- [x] 实现全局/租户 kill switch：规则评估返回 `KILL_SWITCH`，阻止后续自动暂停动作。
- [ ] 规则执行前重新读取最新指标，并二次校验目标仍处于可暂停状态。
- [x] 规则评估生成稳定幂等键；实际动作去重留到 RC-04 执行器消费。
- [ ] 不自动恢复；恢复只能走人工操作，并明确记录原因和审计信息。

**建议涉及文件**：新增 `services/risk_rule_engine.py`、`services/risk_action_service.py`；改造 `services/risk_detector.py`、`services/ads_manager.py`。

**验收**：同一批次重复执行不会重复动作；dry-run、白名单、kill switch 和 cooldown 均有可验证结果。

- [x] 风险事件和止损记录去重；通知持久化投递状态，避免每小时重复告警。

## 四、推荐实施顺序

```text
RC-00 范围与口径
  ↓
RC-01 数据模型/迁移 ──→ RC-02 API/权限
                              ↓
                         RC-03 规则引擎
                              ↓
                         RC-04 任务/止损/通知
                              ↓
                         RC-05 前端闭环
                              ↓
                         RC-06 测试/灰度/上线
```

### 建议分批

| 批次 | 任务 | 重点 | 预估工作量 |
|---|---|---|---:|
| 第 1 批 | RC-00、RC-01 | 统一入口、指标口径、模型和迁移 | 1～2 人日 |
| 第 2 批 | RC-02 | 总览/事件/规则/执行记录 API 与权限 | 2～3 人日 |
| 第 3 批 | RC-03、RC-04 | 规则引擎、安全护栏、幂等动作和调度 | 4～6 人日 |
| 第 4 批 | RC-05 | 总览、事件处理、规则、止损记录页面 | 3～5 人日 |
| 第 5 批 | RC-06 | 回归、构建、灰度和上线检查 | 2～3 人日 |

工作量为实现量级估算，不包含 Meta 账号授权异常、生产数据修复和外部通知渠道审批。
